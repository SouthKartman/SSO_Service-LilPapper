IDENTITY / EXTERNAL AUTH

Внешние провайдеры

Как хранить credentials внешних OAuth/OIDC-провайдеров, настроить существующий провайдер и добавить новый в SSO.

Настройка credentials →Добавить провайдера
ASP.NET Core IdentityOAuth 2.0OpenID ConnectSecrets

CONCEPTS

Два разных уровня интеграции

01

Вход пользователя в SSO

GitHub, Google и другие внешние провайдеры подключаются к ASP.NET Core Identity. Их callback обрабатывает middleware приложения.

02

Клиенты SSO

Сторонние сайты и приложения регистрируются отдельно через OpenIddict/административную панель. Их Client ID и Redirect URI — не credentials GitHub или Google.

IMPORTANT

Не путайте credentials

OAuth Client ID и Client Secret внешнего провайдера используются SSO-сервисом, чтобы входить через этот провайдер. Client ID и секрет клиента SSO используются сторонним приложением для подключения к вашему SSO. Это разные наборы значений.

Хранение

Не сохраняйте секреты провайдеров в PostgreSQL Identity и не отдавайте их браузеру.

STEP 01

Где вводить Client ID и Client Secret

Для локальной разработки используйте .NET User Secrets или переменные окружения. Значения ниже — примеры имён конфигурации, а не готовые credentials. Код приложения должен читать эти ключи из IConfiguration.

Вариант A — .NET User Secrets

Из каталога проекта, где находится файл .csproj, выполните: 

dotnet user-secrets init
dotnet user-secrets set "Authentication:GitHub:ClientId" "YOUR_GITHUB_CLIENT_ID"
dotnet user-secrets set "Authentication:GitHub:ClientSecret" "YOUR_GITHUB_CLIENT_SECRET"

Для Google используйте отдельные ключи:

dotnet user-secrets set "Authentication:Google:ClientId" "YOUR_GOOGLE_CLIENT_ID"
dotnet user-secrets set "Authentication:Google:ClientSecret" "YOUR_GOOGLE_CLIENT_SECRET"

Команды создают локальное хранилище секретов для проекта. Они не добавляют провайдера автоматически: код провайдера должен быть зарегистрирован в Program.cs.

Вариант B — переменные окружения

В ASP.NET Core двойное подчёркивание __ соответствует разделителю : в ключе конфигурации. 

Authentication__GitHub__ClientId=YOUR_GITHUB_CLIENT_ID
Authentication__GitHub__ClientSecret=YOUR_GITHUB_CLIENT_SECRET
Authentication__Google__ClientId=YOUR_GOOGLE_CLIENT_ID
Authentication__Google__ClientSecret=YOUR_GOOGLE_CLIENT_SECRET

В Docker Compose задавайте их через окружение контейнера или файл `.env`, который не хранится в Git. На сервере используйте защищённое хранилище секретов и ограничьте доступ к конфигурации.

Вариант C — appsettings.Development.json

Подходит только для временной локальной настройки, если файл исключён из Git. User Secrets предпочтительнее. 

{
  "Authentication": {
    "GitHub": {
      "ClientId": "YOUR_GITHUB_CLIENT_ID",
      "ClientSecret": "YOUR_GITHUB_CLIENT_SECRET"
    },
    "Google": {
      "ClientId": "YOUR_GOOGLE_CLIENT_ID",
      "ClientSecret": "YOUR_GOOGLE_CLIENT_SECRET"
    }
  }
}
Безопасность: никогда не публикуйте реальные Client Secret, access token или refresh token. Если секрет попал в Git или логи, отзовите его у провайдера и выпустите новый.

STEP 02

Настройки в кабинете провайдера

  1. Создайте OAuth/OIDC-приложение в кабинете нужного провайдера.
  2. Добавьте разрешённый redirect/callback URL, который соответствует настройке middleware в SSO.
  3. Выберите только необходимые permissions/scopes.
  4. Скопируйте Client ID и Client Secret в локальное хранилище секретов или окружение сервера.
  5. Сверьте callback URL посимвольно: схема HTTPS, домен, порт и путь должны совпадать с конфигурацией.

Типичный callback ASP.NET Core middleware выглядит как https://sso.example.com/signin-{scheme}, но фактический путь задаётся настройкой CallbackPath. Не угадывайте его по имени кнопки — сверяйтесь с Program.cs и настройками приложения у провайдера.

Локальные URL с localhost, IP-адресами и нестандартными портами принимаются не всеми провайдерами. Если провайдер требует публичный домен, используйте домен/HTTPS-туннель для тестирования или настройте домен при развёртывании. Само добавление credentials не отменяет требования провайдера к redirect URI.

EXTENSION GUIDE

Как добавить собственного провайдера

Добавление провайдера — это не только ввод Client ID и Client Secret. Нужно зарегистрировать схему аутентификации, настроить callback, получить и проверить claims и добавить провайдера в разрешённый список UI/обработчиков входа.

1. Определите протокол

OpenID Connect

Предпочтителен, если провайдер публикует OIDC discovery, поддерживает стандартный login flow и возвращает проверяемый ID token.

OIDC
OAuth 2.0

Подходит, когда провайдер предоставляет OAuth endpoints и API профиля, но не полноценный OIDC. Обычно требуется отдельный запрос к API и маппинг claims.

OAuth
Нестандартный login API

Если провайдер не поддерживает подходящий стандартный flow, может потребоваться специализированная интеграция. Не считайте любой login widget совместимым с AddOAuth автоматически.

Custom

2. Добавьте credentials в конфигурацию

Например, для собственного провайдера Acme используйте отдельный префикс: 

dotnet user-secrets set "Authentication:Acme:ClientId" "YOUR_CLIENT_ID"
dotnet user-secrets set "Authentication:Acme:ClientSecret" "YOUR_CLIENT_SECRET"

3. Зарегистрируйте схему в Program.cs

Для провайдера, совместимого с OpenID Connect, обычно настраивается OIDC middleware и задаются authority, client ID, secret, scopes и callback. Для обычного OAuth 2.0 применяется OAuth middleware с authorize/token/user-information endpoints и маппингом claims.

Упрощённый пример для стандартного OAuth 2.0-провайдера (не копируйте его без реальных endpoints и схемы ответа конкретного провайдера): 

builder.Services
    .AddAuthentication()
    .AddOAuth("Acme", options =>
    {
        options.ClientId =
            builder.Configuration["Authentication:Acme:ClientId"]!;
        options.ClientSecret =
            builder.Configuration["Authentication:Acme:ClientSecret"]!;

        options.CallbackPath = "/signin-acme";

        // Заполните endpoints, scopes, SignInScheme
        // и ClaimActions по официальной документации Acme.
    });
Этот пример намеренно неполный: без authorize endpoint, token endpoint, UserInformationEndpoint, корректного SignInScheme и claim mapping он не реализует рабочий вход. Если провайдер поддерживает OIDC, предпочтительно использовать OIDC middleware вместо ручной OAuth-настройки.

4. Настройте callback и claims

  • Зарегистрируйте callback path в коде и соответствующий полный HTTPS URL в кабинете провайдера.
  • Настройте внешний cookie/sign-in scheme, который использует ASP.NET Core Identity.
  • Сопоставьте стабильный уникальный идентификатор пользователя провайдера с ClaimTypes.NameIdentifier или эквивалентным OIDC claim sub.
  • Имя и email запрашивайте только при наличии нужных scopes. Не каждый провайдер возвращает email; не используйте email как внешний ProviderKey.
  • Для OAuth API, который возвращает профиль отдельным запросом, реализуйте запрос к user-info endpoint и проверяйте HTTP-ответ и структуру JSON.

5. Добавьте схему в разрешённый список приложения

Если обработчик внешнего входа содержит allowlist, добавьте туда точное имя схемы, например Acme. Добавьте кнопку/форму входа, которая отправляет это имя обработчику. Имя схемы должно совпадать в Program.cs, форме входа и callback-логике.

6. Сохраните связь с локальным пользователем

При первой регистрации создайте ApplicationUser, затем сохраните внешний логин через UserManager.AddLoginAsync(user, info). Для повторного входа сначала используйте существующую привязку. Если email уже занят, не объединяйте аккаунты автоматически только по совпадению email: попросите пользователя войти в существующий аккаунт и пройти отдельный защищённый flow привязки.

7. Проверьте сценарии

  • Новая регистрация: пользователь создан и внешний логин сохранён.
  • Повторный вход: находится существующая привязка.
  • Пустой email: flow не ломается и использует стабильный provider user ID.
  • Занятый email: второй пользователь не создаётся и аккаунты не объединяются автоматически.
  • Ошибка провайдера или отмена входа: показывается безопасное сообщение, секреты и токены не попадают в логи.
  • Callback в production использует HTTPS и точно совпадает с разрешённым URL.

PROJECT STATUS

Credentials не включают провайдера автоматически

Документация описывает общий способ настройки. Поддержка конкретного провайдера появляется только после реализации и проверки соответствующего middleware/API в коде. Google и GitHub имеют собственные настройки; VK ID и Telegram Login могут требовать отдельной OIDC- или специализированной интеграции.

После изменений

Выполните dotnet build, запустите приложение и проверьте регистрацию, повторный вход, отмену авторизации и ошибочные callback.
