Развёртывание SSO на чистом сервере

Порядок переноса ASP.NET Core SSO-сервиса на VPS: подготовка окружения, PostgreSQL, миграции EF Core, HTTPS, проверка OpenID Connect и базовая защита.

Важно. Это шаблон процедуры, а не подтверждение, что проект уже готов к production. Перед запуском сверьте имена сервисов и портов с текущими Dockerfile, compose.yaml и конфигурацией приложения. Не переносите локальные development-сертификаты и секреты на сервер.

1. Что понадобится

  • VPS с поддерживаемым Linux-дистрибутивом и доступом по SSH через ключ.
  • Домен, например sso.example.com, указывающий на публичный IP сервера.
  • Docker Engine и Docker Compose plugin либо другой согласованный способ запуска контейнера.
  • PostgreSQL, доступный приложению по приватной Docker-сети или внутреннему адресу.
  • Текущий исходный код проекта и проверенная сборка для .NET 10.

2. Подготовить сервер

Обновите систему, установите Docker по официальной инструкции для своего дистрибутива и проверьте версии: 

docker --version
docker compose version

Создайте каталог развёртывания, например:

sudo mkdir -p /opt/sso
sudo chown "$USER":"$USER" /opt/sso
cd /opt/sso

Скопируйте проект или разверните его из репозитория в выбранный каталог. Не помещайте файл с секретами в Git.

3. Настроить параметры окружения

В проекте строка подключения читается из ConnectionStrings:SsoDatabase; в переменных окружения ASP.NET Core ей соответствует ConnectionStrings__SsoDatabase.

Пример значений для файла окружения — замените все демонстрационные значения: 

# .env — не коммитить в Git и ограничить права доступа
ASPNETCORE_ENVIRONMENT=Production
ConnectionStrings__SsoDatabase=Host=postgres;Port=5432;Database=sso_auth;Username=sso_app;Password=REPLACE_WITH_LONG_RANDOM_SECRET
Если PostgreSQL запущен как сервис Compose, Host=postgres работает только тогда, когда сервис действительно называется postgres и находится в той же сети. Имя хоста должно совпадать с вашей конфигурацией.

Ограничьте доступ к файлу с секретами:

chmod 600 .env

В production также задайте публичный issuer через конфигурацию приложения, если код поддерживает его настройку: https://sso.example.com/. Адрес issuer должен совпадать с внешним адресом сервиса и оставаться стабильным.

4. Подготовить PostgreSQL

Создайте отдельную базу и отдельного пользователя приложения с минимально необходимыми правами. Не открывайте порт PostgreSQL в публичный интернет: подключение должно идти из внутренней сети или через защищённый административный канал.

Перед миграцией проверьте, что соединение из контейнера приложения работает. Не используйте EnsureCreated() для базы, управляемой EF Core migrations: применяйте существующие миграции.

5. Собрать и запустить контейнеры

Команды ниже — типовой порядок. Запускайте их из каталога, где расположен ваш Compose-файл; названия сервисов должны соответствовать реальному файлу. 

# Проверить итоговую конфигурацию Compose
docker compose config

# Собрать образы
docker compose build

# Запустить PostgreSQL и приложение
docker compose up -d

# Проверить состояние и логи
docker compose ps
docker compose logs --tail=200
Не копируйте в production случайный Dockerfile или Compose-файл из примера без сверки. Проверьте, что контейнер приложения слушает порт, на который настроен reverse proxy, а база не публикует порт наружу.

6. Применить миграции EF Core

Миграции должны создавать таблицы ASP.NET Core Identity и OpenIddict, а также все таблицы, определённые текущим ApplicationDbContext. Сначала проверьте наличие миграций в репозитории.

Если в проекте установлен dotnet-ef и SDK доступен в среде выполнения команд: 

dotnet tool restore
dotnet ef migrations list
dotnet ef database update

Если приложение запускается только в контейнере, выполните миграцию из контейнера/одноразового migration-контейнера с теми же сборкой и переменными окружения. Не устанавливайте SDK в production runtime-образ только ради миграций, если для этого предусмотрен отдельный процесс.

Если dotnet ef database update не видит проект или контекст, укажите актуальные параметры --project и --startup-project согласно расположению sso-service.csproj. Не создавайте новую миграцию на сервере для исправления отсутствующей миграции в репозитории.

7. Настроить HTTPS и reverse proxy

  1. Направьте DNS-запись домена на VPS.
  2. Настройте reverse proxy (например, Nginx или Caddy) для завершения TLS и проксирования запросов к внутреннему HTTP-порту приложения.
  3. Передавайте исходные схему и host через стандартные заголовки прокси и настройте ASP.NET Core Forwarded Headers для доверенного прокси.
  4. Ограничьте доверие к forwarded-заголовкам конкретным прокси/сетью; не принимайте их безусловно от произвольных клиентов.
  5. Проверьте автоматическое продление сертификата и обновление конфигурации после продления.

Обычно наружу открывают только SSH и веб-порты 80/443. Внутренний порт приложения и PostgreSQL не должны быть доступны всему интернету.

8. Сертификаты OpenIddict и ключи

В production замените development signing/encryption certificates на подходящие production-сертификаты или управляемое хранилище ключей. Защитите приватные ключи, ограничьте доступ к ним и организуйте ротацию.

Сохраните постоянные ASP.NET Core Data Protection keys между перезапусками и обновлениями контейнера, если приложение использует cookie authentication. Для нескольких экземпляров все экземпляры должны использовать согласованное хранилище ключей и общий application name.

Не генерируйте новый signing key при каждом старте. Это может сделать уже выданные токены непроверяемыми. Не используйте UseDevelopmentSigningCertificate() и UseDevelopmentEncryptionCertificate() как production-настройку.

9. Первый запуск и администратор

  1. Откройте публичный адрес https://sso.example.com/.well-known/openid-configuration.
  2. Убедитесь, что в metadata endpoint-ы указывают на публичный HTTPS-домен, а не на localhost или внутреннее имя контейнера.
  3. Проверьте регистрацию и вход, если они включены в текущей конфигурации.
  4. Создайте обычную учётную запись, затем назначьте ей роль Admin контролируемым способом, предусмотренным проектом.
  5. Откройте /Admin/Applications и зарегистрируйте клиентское приложение.
  6. Пройдите OAuth-тест на /oauth-test.html только если эта тестовая страница предназначена для окружения. Для публичного production-сервиса ограничьте или удалите тестовые инструменты.

10. Проверки перед публикацией

  • В конфигурации нет issuer https://localhost:7076/, тестовых Client ID или development-сертификатов.
  • В логах нет паролей, access/refresh tokens, cookie или приватных ключей.
  • PostgreSQL не опубликован на публичный интерфейс; резервные копии создаются и проверяются.
  • Cookie настроены безопасно для HTTPS, а HTTPS redirect и forwarded headers работают корректно.
  • Redirect URI каждого OAuth-клиента проверяется на точное совпадение; wildcard и произвольные callback URL не разрешены.
  • Для production отключены или защищены Swagger, тестовая OAuth-страница и другие диагностические маршруты.
  • Есть мониторинг свободного места, доступности БД, ошибок приложения и срока действия сертификатов.

11. Обновление приложения

  1. Сделайте резервную копию PostgreSQL и проверьте возможность восстановления.
  2. Проверьте изменения схемы и совместимость миграций с предыдущей версией приложения.
  3. Соберите и проверьте новый образ.
  4. Примените миграции согласно выбранной стратегии релиза.
  5. Перезапустите сервис, проверьте health/logs, Discovery и тестовый вход.
  6. При ошибке используйте заранее подготовленный план отката; откат схемы БД не всегда безопасен автоматически.

12. Полезные команды диагностики

# Статус контейнеров
docker compose ps

# Последние логи сервиса
docker compose logs --tail=200 sso-service

# Проверка HTTP-ответа Discovery с сервера
curl -fsS https://sso.example.com/.well-known/openid-configuration

# Используйте реальное имя сервиса из compose.yaml

Команда логов выше предполагает имя сервиса sso-service; если в вашем Compose оно другое, замените его.
