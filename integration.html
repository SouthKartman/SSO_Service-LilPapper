INTEGRATION GUIDE

Подключение приложения к SSO

Руководство описывает общий процесс подключения стороннего приложения к серверу OpenID Connect. Значения адресов и разрешений необходимо сверять с текущей конфигурацией вашего SSO.

ШАГ 01

Регистрация клиента

До начала интеграции приложение должно быть зарегистрировано администратором SSO. Для каждого приложения используются собственные Client ID и разрешённые адреса возврата.

  1. Откройте административную панель SSO.
  2. Создайте приложение с уникальным Client ID.
  3. Укажите точный Redirect URI.
  4. Выберите тип клиента и необходимые scopes.
  5. Сохраните настройки и проверьте запись в списке приложений.
Public и Confidential

Public-клиент не может безопасно хранить секрет в браузере. Confidential-клиент должен хранить секрет на доверенном сервере. Для браузерных приложений рекомендуется Authorization Code Flow с PKCE.

ШАГ 02

Получение конфигурации

Используйте OIDC Discovery, чтобы получить адреса авторизации и обмена кода на токен. 

GET /.well-known/openid-configuration

В локальной конфигурации проекта адрес обычно выглядит так: https://localhost:7076/.well-known/openid-configuration. В production используйте фактический HTTPS-адрес сервера.

В JSON-конфигурации найдите issuer, authorization_endpoint и token_endpoint. Не предполагайте, что адреса всегда совпадают с локальным примером.

ШАГ 03

Запуск авторизации

Приложение генерирует случайный code_verifier, вычисляет для него SHA-256 challenge и создаёт случайный state для защиты OAuth-запроса.

Затем браузер перенаправляется на authorization_endpoint с параметрами:

  • client_id — идентификатор зарегистрированного клиента;
  • redirect_uri — адрес, разрешённый в настройках клиента;
  • response_type=code — запрос кода авторизации;
  • scope=openid — запрос OpenID Connect;
  • state — случайное значение для проверки ответа;
  • code_challenge и code_challenge_method=S256 — параметры PKCE.
Проверяйте state

При возврате на callback приложение должно проверить, что полученный state совпадает со значением, сохранённым перед перенаправлением.

ШАГ 04

Обработка callback

После успешной авторизации SSO возвращает браузер на зарегистрированный Redirect URI с параметром code и исходным state.

Приложение проверяет state и отправляет код на token_endpoint. Вместе с кодом передаются Client ID, тот же Redirect URI и исходный PKCE verifier.

Код авторизации одноразовый и имеет ограниченный срок действия. При ошибке callback следует обработать параметры error и error_description, если они присутствуют.

ШАГ 05

Работа с токенами

  • ID token содержит утверждения об аутентификации пользователя в рамках OpenID Connect.
  • Access token предназначен для доступа к ресурсам, которые принимают этот токен.
  • Refresh token позволяет получать новые токены, если сервер выдал его и клиенту разрешён соответствующий поток.

Не считайте любой access token JWT и не пытайтесь использовать его как ID token. Формат и аудитория токена зависят от настроек сервера и защищённого API.

TROUBLESHOOTING

Типичные ошибки

  • invalid_client — проверьте регистрацию и способ аутентификации клиента.
  • invalid_redirect_uri — сверьте Redirect URI с регистрацией.
  • invalid_grant — проверьте код, Redirect URI и PKCE verifier.
  • unauthorized_client — проверьте разрешённые типы запросов и потоки.
  • Ошибка браузерного запроса — проверьте CORS, HTTPS и сетевые ошибки.
